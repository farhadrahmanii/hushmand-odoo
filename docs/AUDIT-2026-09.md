# Pre-sale audit, September 2026

Nine confirmed defects, found before the first sale. None had been caught by
the 546 passing tests, because the tests assert what the author expected.

**Method.** Four independent reviewers read the code that handles money and
access. Each finding was then attacked by two skeptics — one trying to refute
the code claim, one trying to prove no real user could reach it — and the tax
arithmetic was worked by hand against the shipped brackets. Findings no
attacker could kill are below.

**A caution about the run itself.** Half the verifier agents died on a session
limit, and the harness reported their findings as *refuted, with no reason* —
which is exactly how a real defect gets buried. Those seven were re-checked by
hand; four were confirmed (T1–T3, L2) and appear here. If this audit is re-run,
never read an empty refutation reason as a refutation.

## P1 — A cancelled advance still deducts, and re-approving deducts again

`addons/hm_payroll/models/hm_salary_advance.py:191` — **high**

`action_cancel` guards only on `amount_recovered`, which stays zero until a
payslip is *confirmed*. So while a draft payslip holds a claim:

1. An advance of 12,000 over 3 instalments is approved.
2. January's payslip is computed: the instalment is claimed and a stored
   deduction line of −4,000 is written into `line_ids`.
3. HR cancels the advance. The guard passes (nothing recovered yet), line 191
   clears `payslip_id`, the advance goes to `cancelled`.
4. The payslip is confirmed. `action_confirm` checks only `state` and
   `line_ids` — it never re-derives the advance. **The −4,000 is posted and the
   employee is paid short for an advance that was cancelled.**
5. `advance_line_ids.write({"recovered": True})` now runs on an empty
   recordset, silently recording nothing.
6. Reset to draft, re-approve: the schedule is rebuilt and the full 12,000 is
   recovered again. **16,000 taken for a 12,000 advance.**

Reachable by an ordinary Payroll Officer through shipped buttons. The batch
**Confirm All** makes step 4 part of the normal month-end flow.

Fix at either end: `action_cancel` refuses while a draft payslip holds a claim,
or `action_confirm` re-derives the advance before freezing.

## P2 — A paid payslip can be cancelled

`addons/hm_payroll/models/hm_payslip.py:500` — **medium**

`action_cancel` is the only transition on the model with no state guard, so a
payslip already `paid` can be cancelled. That returns its advance instalments
to unrecovered and lets the next payslip deduct them a second time.

## P3 — No multi-company isolation on payroll at all

`addons/hm_payroll/security/hm_payroll_security.xml:32` — **critical**

`hm_payroll` ships **no `ir.rule` records**. There is no multi-company rule on
`hm.payslip`, `hm.payslip.line`, `hm.payslip.run`, `hm.salary.advance`,
`hm.payroll.structure` or `hm.salary.rule`.

Every payroll officer sees and can edit **every company's** salary data in the
database. For a customer running two companies in one Odoo — which the
catalogue's own `company_id` fields invite — that is a breach of the most
sensitive table in the system.

## P4 — An employee can approve their own timesheet

`addons/hm_timesheet/models/hm_timesheet_sheet.py:192` — **high**

`write()` has no guard on `state`, and the ACL grants every ordinary employee
write on their own sheet. So `sheet.write({"state": "approved"})` — one ORM
call, or an import — approves it, bypassing the entire approval workflow the
module exists to provide.

## P5 — The timesheet lock can be stepped around

`addons/hm_timesheet/models/account_analytic_line.py:94` — **high**

`sheet_id` is in `STRUCTURAL_FIELDS`, so a write touching only `sheet_id` skips
`_check_sheet_open`. An employee can detach an entry from an approved week,
change the hours, and re-attach it.

The exemption exists so the module can attach entries to sheets. It does not
distinguish the module doing that from a user doing it.

## T1 — Semi-monthly payroll over-withholds on every slip

`addons/af_hr_payroll/models/hm_payslip.py:75` — **high**

`_af_periods_per_year` has no semi-monthly bucket. A 15-day period falls into
`if days <= 20: return 26.0`, so it is annualised ×26 instead of ×24.

Worked against the shipped brackets, salary AFN 40,000/month:

| Paid | Tax per month |
|---|---|
| Monthly (30 days, ppy=12) | 2,900.00 |
| 1st–15th + 16th–end (ppy=26) | **2,984.62** |
| Correct (ppy=24) | 2,900.00 |

**84.62 AFN over-withheld per employee per month, ~1,015 AFN a year**, on 100%
of slips, permanently and silently.

## T2 — Every mid-month starter and leaver is taxed as a fortnightly worker

`addons/af_hr_payroll/models/hm_payslip.py:75` — **high**

The same ladder infers *pay frequency* from *period length*, so a part-month
slip is read as a more frequent payroll. Someone joining on the 12th on
40,000/month:

- 19 days worked, gross 25,333.33
- the ladder returns ppy=26, tax charged **2,025.64**
- treated as the monthly payroll it actually is: **1,433.33**
- **overcharged 592.31 AFN — 41% too much** — on their first payslip

## T3 — More days worked, less tax

`addons/af_hr_payroll/models/hm_payslip.py:73-81` — **high**

The ladder is a step function over a continuous quantity, so tax is not
monotonic in days worked:

| Days | Gross | ppy | Tax |
|---|---|---|---|
| 20 | 26,666.67 | 26.0 | **2,158.97** |
| 21 | 28,000.00 | 12.0 | **1,700.00** |

One more day worked, 1,333 more earned, **459 AFN less tax**. Indefensible to
an auditor and impossible to explain to an employee.

T1–T3 share one root cause: frequency is *guessed* from period length. The
payslip should carry its pay frequency — from the structure or the batch —
rather than infer it.

## T4 — The bracket validator never runs on the shipped scale

`addons/af_hr_payroll/models/af_income_tax.py:60` — **medium**

`_check_brackets_are_a_scale` is `@api.constrains("bracket_ids")` on the
*scale*. The shipped brackets are standalone
`<record model="af.income.tax.bracket">` entries with a `scale_id` ref —
created through the inverse, never through the scale's one2many — so **the
constraint has never fired on the data the product ships with**, and will not
fire for a customer importing next year's brackets the same way.

Combined with `compute_tax`, which initialises `tax_monthly = 0.0` and can skip
every bracket: a scale whose top bracket is capped returns **zero tax** for any
salary above the cap, silently.

The module's README states that a gapped scale "is refused". It is not, on the
loading path it ships with. Move the constraint onto the bracket model.

## L1 — One licence key works in unlimited databases

`addons/hm_license/models/hm_license.py` — **medium**, arguably by design

A key is bound to nothing: no database UUID, no instance fingerprint. One
purchased licence verifies as fully valid in any number of installations, and
the per-database user cap is multiplied by however many copies exist.

Offline verification cannot phone home, but it *can* bind to the database UUID.
Worth deciding deliberately rather than leaving implicit.

## L2 — Licence fields can be rewritten without re-checking the signature

`addons/hm_license/models/hm_license.py:302` — **medium**

```python
def write(self, vals):
    result = super().write(vals)
    if "key" in vals:
        self.action_verify()
```

`expires`, `max_users` and `modules` are stored fields marked `readonly=True` —
which is a UI constraint only. A system administrator can write them directly
via ORM, an import, or developer mode, and the signature is never re-checked
against the new values.

The attacker must already be an administrator, who could also edit the Python.
But editing Python needs filesystem access and is undone by the next upgrade;
an import file is a few clicks, leaves the code pristine, and survives upgrades.
